Связанные документы: [FEATURE_BACKLOG](FEATURE_BACKLOG.md) · [USER_JOURNEY](USER_JOURNEY.md) · [FLYPING_STRATEGY](FLYPING_STRATEGY.md) · [KPI](KPI.md)

**Статус:** в работе по частям.  
**Сделано:** AN-03 (лог алертов + тесты + миграция).  
**Остальное ядро** — ждёт отдельных подтверждений / ревью AN-03.
  
**Цель спринта:** закрыть P0-дыры в воронке «watch → алерт» (антиспам, ясность контракта, достижимый порог, измеримость NSM), не трогая рост/premium/тяжёлый хостинг.  
**North Star:** Alerted Watchers (30d).  
**Оценка объёма:** ~5–8 человеко-дней (1 разработчик).

## Задачи спринта

### 1. NT-04 — Антиповтор / cooldown по `last_alert_price`

| Поле | Содержание |
|------|------------|
| **Feature ID** | NT-04 |
| **Краткое описание** | Не слать повторный алерт, если цена всё ещё ≤ порога, но не стала заметно выгоднее прошлого алерта (или не вышел cooldown). |
| **Обоснование выбора** | USP «молчит до события»; Value 9 / Effort 3; Journey шаг 4 — главный риск Block из‑за спама; поле `last_alert_price` уже пишется, логика глушения отсутствует. |
| **Зависимости** | NT-01 (Done); поле в `Watch` (есть). Решение правила зафиксировать в DECISIONS. |
| **Ожидаемый результат** | При стабильной цене пользователь получает один алерт, не пачку на каждый цикл scheduler. |
| **Критерии готовности** | Правило в коде + тест(ы); запись в DECISIONS; ручная проверка: два `run_once` подряд без изменения цены → один алерт. |
| **Влияние на NSM** | **High** — retention watches → больше шансов остаться Alerted Watcher, а не удалить бота. |
| **Риски** | Слишком жёсткий cooldown → пропуск реального нового минимума; слишком мягкий → спам остаётся. Нужны явные константы (например: алерт снова только если цена ↓ на X% или на Y ₽, или через N часов). |

### 2. NT-02 — Явный контракт порога в тексте алерта

| Поле | Содержание |
|------|------------|
| **Feature ID** | NT-02 |
| **Краткое описание** | В каждом алерте явно: текущая цена X, порог Y, факт «X ≤ Y» / дельта. |
| **Обоснование выбора** | Value 8 / Effort 2; Compete O1; formatters частично умеют порог — довести единообразие в пути checker → сообщение. |
| **Зависимости** | NT-01 (Done). |
| **Ожидаемый результат** | Пользователь с первого взгляда понимает, *почему* пришло уведомление. |
| **Критерии готовности** | Все алерты из `PriceChecker` содержат X, Y и сравнение; нет двусмысленного «цена изменилась» без порога. |
| **Влияние на NSM** | **Medium** — ↑ доверие и вероятность клика; ↓ отписки от «непонятных» пушей. |
| **Риски** | Длинный текст в Telegram; нужно не сломать HTML parse_mode. |

### 3. NT-03 — Вилка рынка внутри алерта

| Поле | Содержание |
|------|------------|
| **Feature ID** | NT-03 |
| **Краткое описание** | В алерте кратко 🟢/🟡/🔴 и ориентир «обычно ~median» (band уже считается в checker). |
| **Обоснование выбора** | Value 8 / Effort 2; Compete O3; band уже в pipeline `run_once`. |
| **Зависимости** | NT-01 (Done); `get_trip_band` в checker (есть). Логично делать сразу после/вместе с NT-02 (один шаблон сообщения). |
| **Ожидаемый результат** | Алерт отвечает: «дешёво ли это относительно рынка *сейчас*». |
| **Критерии готовности** | Band в алерте при наличии данных; fallback без падения, если band `None`. |
| **Влияние на NSM** | **Medium** — сильнее решение открыть билеты (leading к CPA; retention через полезность). |
| **Риски** | Band устарел относительно quote; для RT band может путать — сохранить текущую честность дисклеймеров. |

### 4. CS-05 — Предупреждение «порог ниже рынка»

| Поле | Содержание |
|------|------------|
| **Feature ID** | CS-05 |
| **Краткое описание** | При выборе/вводе порога ≪ P25 (дёшево) — явное предупреждение, что алертов почти не будет; сохранить всё равно можно. |
| **Обоснование выбора** | Value 8 / Effort 2; Strategy must-have; Journey шаг 3 — главная причина «тихих» мёртвых watches. |
| **Зависимости** | CS-02 (Done, вилка есть) в боте и Mini App. |
| **Ожидаемый результат** | Меньше подписок с заведомо недостижимым порогом. |
| **Критерии готовности** | Предупреждение в FSM (кнопки + custom price) и в Mini App; можно подтвердить порог после предупреждения; порог = P25/typical без ложного варна. |
| **Влияние на NSM** | **High** — прямо ↑ доля watches, которые когда-либо получат алерт. |
| **Риски** | Ложный варн при кривой/пустой вилке; разный UX бот vs Mini App — сделать оба. |

## Рекомендуемый порядок реализации

```text
1. CS-08     — убедиться, что прод не в demo (иначе остальное тестировать бессмысленно)
2. AN-03     — схема лога алертов (миграция)
3. NT-04     — антиспам + писать в AN-03 только при реальной отправке
4. NT-02     — текст контракта порога в шаблоне алерта
5. NT-03     — вилка в том же шаблоне алерта  (можно одним PR с NT-02)
6. CS-05     — варн порога в боте + Mini App
7. TR-04     — timestamp в карточках и алерте
8. RL-02     — версии + CHANGELOG
9. IT-02     — тесты (stretch / хвост)
10. WA-02    — только если подтверждён хостинг (stretch)
```

**Почему такой порядок:** сначала честные цены и измерение, затем поведение алертов (спам → текст), затем создание watch (порог), затем косметика доверия (timestamp) и релизные мелочи.

**Логичные PR-срезы (предложение):**

1. `CS-08` (ops note) + `RL-02`  
2. `AN-03` + `NT-04` (+ `IT-02` тесты)  
3. `NT-02` + `NT-03` + `TR-04` (шаблоны сообщений)  
4. `CS-05` (бот + Mini App)

## Definition of Done спринта

- [ ] Все задачи ядра 1–8 в статусе Done по своим DoD  
- [ ] `pytest -q` зелёный  
- [ ] Ручной прогон: создать watch → два цикла check без смены цены → **один** алерт с X≤Y и вилкой  
- [ ] Можно выполнить SQL/скрипт Alerted Watchers за 30d (хотя бы на тестовых данных)  
- [ ] Обновлены: FEATURE_BACKLOG статусы, CHANGELOG, при необходимости DECISIONS (правило антиспама)  
- [ ] **Код не начат до подтверждения этого документа**
