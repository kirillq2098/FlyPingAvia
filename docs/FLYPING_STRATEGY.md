# FlyPing Strategy

Связанные документы (не дублируем их здесь): [Vision](PRODUCT_VISION.md) · [Roadmap](MASTER_ROADMAP.md) · [Competitive Analysis](COMPETITIVE_ANALYSIS.md) · [Monetization](MONETIZATION.md) · [KPI](KPI.md) · [Decisions](DECISIONS.md)

**Назначение файла:** зафиксировать *как* FlyPing выигрывает на длинной дистанции — позиционирование, фокус, метрика успеха, логика роста и правила выбора фич.  
**Статус:** рабочая стратегия на базе MVP 0.2.0. Утверждённые решения vs гипотезы помечены явно.

---

## 1. Почему пользователь выберет FlyPing

Пользователь выбирает FlyPing не потому, что «тут больше авиакомпаний», а потому что:

1. **Контракт понятен.** «Напиши, когда цена станет ≤ моего порога» — жёстче, чем «уведомим при значительном изменении» у Google Flights / процентные алерты KAYAK ([COMPETITIVE_ANALYSIS](COMPETITIVE_ANALYSIS.md)).
2. **Живёт там, где он уже сидит.** Telegram-чат + Mini App, без установки ещё одного travel-app (слабость Trip.com / Skyscanner / Momondo как суперapps).
3. **Решение в одном сообщении.** Порог, цена, контекст рынка (вилка), ссылка на билеты — без возврата в тяжёлый UI поиска.
4. **Честные ожидания.** Не mistake-fare sniper и не «мгновенность Google»; «проверили только что» + ручная проверка ([O7](COMPETITIVE_ANALYSIS.md)).

**Гипотеза сегмента (Vision TODO не закрыт):** первый платящий вниманием пользователь — русскоязычный самостоятельный турист с 1–2 конкретными поездками в году (отпуск / визит), который уже смотрел цены в Aviasales и устал обновлять вкладку. Не командировочный корпоративный buyer и не охотник за error fare.

**Прямой конкурент за привычку:** официальный бот Aviasales. Выбор FlyPing против него — **гипотеза:** уже UX порога, меньше шума, сильнее «относительно рынка» в алерте; не «лучше искать билеты».

## 2. Уникальное торговое предложение (USP)

> **FlyPing — сторож цены в Telegram: вы задаёте потолок в рублях, бот молчит, пока потолок не достигнут, и тогда даёт один понятный шаг к билетам.**

Разложение USP:

| Элемент | Почему уникален относительно рынка |
|---------|-------------------------------------|
| Потолок в ₽ | Не «significant change» / не только «цена упала» |
| Молчит до события | Антиспам как часть обещания, не afterthought |
| Telegram-native | Канал доставки = продукт, не приложение вокруг поиска |
| Один клик к покупке | CPA на Aviasales; FlyPing не касса |

**Не USP (и не пытаемся им стать):** самый широкий поиск, самые низкие «склеенные» тарифы, Price Freeze, свой OTA.

## 3. Какие проблемы решаем лучше конкурентов

Только там, где у конкурентов системная слабость, а у нас есть (или почти есть) рычаг:

| Проблема пользователя | Почему конкуренты слабее | Как FlyPing отвечает |
|-----------------------|--------------------------|----------------------|
| Неясно, *когда* реагировать на уведомление | Размытый критерий алерта | `price ≤ max_price` как контракт |
| Не хочу ставить app ради одной поездки | App/email-centric гиганты | Бот + Mini App |
| Не знаю, хороший ли это прайс | Алерт без рыночного контекста | Вилка дёшево/обычно/дорого |
| Заваливают уведомлениями | Digests / каждый сдвиг цены | Политика на базе `last_alert_price` (обязательна к доведению) |
| Устал сравнивать вкладки | Metasearch как работа | Режим «поставил и забыл» |

**Чего мы не обещаем решать лучше:** найти самый экзотический стыковочный тариф (Kiwi), предсказать рынок лучше Hopper, заменить Aviasales как витрину поиска.

## 4. Какие функции обязательны

«Обязательно» = без этого USP разрушается или продукт нельзя честно продавать. Не весь backlog.

### Must-have сейчас (до масштаба роста)

1. **Создание и хранение подписки** (маршрут, даты, порог, active/soft-delete).  
2. **Фоновая проверка цен** с предсказуемым интервалом.  
3. **Алерт по контракту порога** с партнёрской ссылкой.  
4. **Вилка рынка при выборе порога** (иначе порог ставят вслепую).  
5. **Стабильная доставка в Telegram** (бот up + при Mini App — стабильный HTTPS URL).  
6. **Антиповтор алертов** (использовать `last_alert_price` / cooldown) — иначе USP «молчит» ложный.  
7. **Реальные цены Travelpayouts** на проде (не demo) для любого внешнего пользователя.

### Must-have до осмысленного роста (этап B roadmap)

8. **Измерение цепочки алерт → клик → (по возможности) бронь** хотя бы через кабинет Travelpayouts + минимальная внутренняя метка.  
9. **Timestamp последней проверки** в карточке/алерте.  
10. **Понятный онбординг порога** (пресеты + предупреждение, если порог ниже рынка).

### Must-have для масштаба каналов (к 1k–10k)

11. **Deep-link / источник трафика** (`?start=`) и **sub-marker** для атрибуции.  
12. **Шаринг карточки подписки** (рост без платного CAC).

Всё остальное из README (календарь дешевизны, SEO-сайт, B2B API, подписка) — *не* must-have, пока не выполнены пункты выше.

## 5. Что нельзя делать (чтобы не потерять фокус)

Явные **non-goals** до доказанной юнит-экономики CPA (или явного пересмотра этой стратегии в [DECISIONS](DECISIONS.md)):

| Не делаем | Почему |
|-----------|--------|
| Native iOS/Android | Высокая стоимость; Telegram уже канал; см. O9 |
| Свой booking / касса | Другой бизнес, поддержка, PCI/жалобы |
| Price Freeze / fintech-хедж | Капитал + регуляторика (урок Hopper) |
| Virtual interlining / self-transfer | Риск доверия (урок Kiwi), не наш USP |
| «Ещё один Aviasales» (полный metasearch UI) | Конкурируем с владельцем инвентаря, на котором зарабатываем |
| Отели, страховки, туры как ядро | Размывает watchdog; допустимо только как CPA-хвост *после* трафика |
| Публичный B2B API раньше стабильного B2C | Roadmap сам откладывает; иначе обслуживание чужих SLA |
| Гонка за mistake fares / ultra-low latency | Невыполнима против Google/deal-сервисов; ломает честный оффер |
| Включение UI пассажиров без доступа Flight Search | Уже осознанно скрыто; иначе врём в цене |

**Правило:** если фича не усиливает контракт порога, тишину до события или путь «алерт → билеты» — она вне фокуса.

## 6. North Star Metric

### Выбор

**North Star: число пользователей с ≥1 активной подпиской, которым за последние 30 дней ушёл ≥1 валидный алерт по контракту порога.**

Рабочее имя: **Alerted Watchers (30d)**.

### Почему одна эта, а не выручка или «просто users»

| Кандидат из [KPI](KPI.md) | Почему не North Star сейчас |
|---------------------------|------------------------------|
| Все users в БД | Мёртвые `/start` без подписки |
| Active watches | Можно копить watches без полезных алертов (плохой порог / спам / простой) |
| CPA revenue | Лагирует и зависит от кабинета партнёра; пока нет стабильного трекинга — плохой руль |
| Alert → click | Правильный *коммерческий* KPI, но сегодня **не измеряется в продукте** |

Alerted Watchers требует одновременно: человек остался, подписка жива, проверка работает, порог достижим, алерт доставлен. Это ближайший измеримый proxy ценности из Vision («вовремя купить по приемлемой цене»).

### Вторичные метрики (не North Star)

- **Leading:** доля новых users → ≥1 watch за 24ч; watches / user.  
- **Quality:** доля алертов без повтора той же цены (антиспам).  
- **Lagging commercial:** клики и брони по marker в Travelpayouts; revenue / Alerted Watcher.  
- **Ops:** публичный `/api/health` uptime.

### Цели по масштабу

**Гипотеза** (цифры не из данных продукта — калибровать после первых замеров):

| Масштаб users* | Ориентир Alerted Watchers (30d) |
|----------------|--------------------------------|
| 100 | 30–50 |
| 1 000 | 250–400 |
| 10 000 | 2 000–3 500 |
| 100 000 | 15 000–30 000 |

\*users = записи в `users`. Конверсия Alerted Watchers / users — главный health-check роста.

## 7. Первые 100 пользователей

**Цель этапа:** доказать, что контракт порога понятен и сервис не стыдно показать человеку вне команды.

| Фокус | Действие |
|-------|----------|
| Кого берём | Личный круг + 2–3 travel-чата/знакомых; **гипотеза** — люди с реальной поездкой в горизонте 1–6 мес. |
| Продукт | Стабильный бот; live Travelpayouts; антиспам алертов; честный копирайт про 1 взрослого и RT≈2×OW |
| Канал | Ручной onboarding, без блогеров и SEO |
| Успех | ≥40% создали watch; ≥10 человек получили осмысленный алерт; 5+ качественных интервью «понял ли порог / мешал ли шум» |
| Провал | Mini App недоступен днями; demo-цены снаружи; алерты дублируются каждые N минут |

Деньги на этом этапе не цель — цель *сигнал*, что North Star может расти без стыда за продукт.

---

## 8. Первые 1 000 пользователей

**Цель этапа:** повторяемый органический/полуорганический канал + первая юнит-экономика.

| Фокус | Действие |
|-------|----------|
| Продукт | Deep-link `?start=`; шаринг карточки; timestamp проверки; усиленный онбординг порога |
| Канал | **Гипотеза primary:** 3–10 mid-size travel/Telegram-креаторов с sub-marker; secondary — шаринг между пользователями |
| Измерение | Сверка Travelpayouts по marker; хотя бы грубый alert→click |
| Успех | Alerted Watchers растёт неделю к неделе; известен лучший канал по CPA; нет зависимости от одного ephemeral tunnel |
| Монетизация | Только CPA; freemium-лимит — **решение отложить**, пока не видно abuse (сейчас лимит выключен) |
| Провал | Рост users без алертов (мёртвые подписки); CAC креатора > ожидаемой CPA-маржи (**гипотеза** порога окупаемости — считать после 50+ броней в кабинете) |

---

## 9. Первые 10 000 пользователей

**Цель этапа:** продукт выдерживает нагрузку привычки; появляется рычаг монетизации сверх «просто маркер».

| Фокус | Действие |
|-------|----------|
| Продукт | Надёжный хостинг (домен/VPS/named tunnel); возможный вынос checker; политика лимитов при abuse; тихие часы |
| Данные | Postgres **гипотеза** — когда SQLite/один процесс упирается (порог N watches — измерить, не гадать заранее) |
| Рост | Несколько стабильных креатор-каналов + шаринг; SEO/лендинг — только если Telegram-каналы насыщены |
| Монетизация | Рассмотреть freemium (включить `FREE_WATCH_LIMIT`) **или** лёгкую платную полку *после* данных этапа 1k; содержимое полки — **гипотеза** (больше watches / чаще check / приоритет) |
| Успех | Стабильный Alerted Watchers / users; положительная или близкая к нулю unit-экономика на лучшем канале; инциденты uptime &lt; терпимого порога (порог задать в DECISIONS) |
| Не делать | Native apps, Freeze, свой OTA, B2B API |

---

## 10. Первые 100 000 пользователей

**Цель этапа:** FlyPing — узнаваемый watchdog в RU Telegram, а не «ещё один бот на TP API».

| Фокус | Действие |
|-------|----------|
| Продукт | Масштаб инфраструктуры; возможно multi-source цен; pax UI **только** при доступе Flight Search |
| Бренд | Отстройка от Aviasales bot сформулирована в одном предложении и подтверждена данными (меньше шума / выше доля алертов с кликом) — иначе пересмотр USP |
| Монетизация | CPA + осмысленная подписка и/или B2B **после** B2C-привычки; ancillaries только как хвост |
| Организация | Юрконтур под выплаты и налоги; не один человек на support 24/7 — **гипотеза** порога найма |
| Успех | North Star на целевом уровне; выручка покрывает хостинг+маркетинг+минимальную команду; доля Alerted Watchers не размыта «мусорным» трафиком |
| Риск | Стать thin UI над Aviasales без собственной ценности → тогда либо углублять watchdog-качество, либо честно pivot |

100k — **не** цель «ради vanity». Это горизонт, на котором стратегия либо подтверждена экономикой, либо переписывается.

## 11. Основные продуктовые риски

| Риск | Почему реален | Митигация |
|------|---------------|-----------|
| Зависимость от Travelpayouts/Aviasales | Цены + деньги + редирект в одних руках | Честный оффер; не строить кассу; следить за ToS/доступом API; не врать в demo |
| Прямое поглощение сценария ботом Aviasales | У них бренд и Telegram | Скорость на антиспам + порог + вилка в алерте; измеримое отличие |
| Ephemeral HTTPS / падение Mini App | Уже болели на trycloudflare | Stable host до любого внешнего трафика |
| «Пустые» подписки | Порог ниже рынка → 0 алертов → churn | Онбординг порога; пресеты; предупреждения |
| Спам алертами | `last_alert_price` не глушит | P0 до роста |
| Невидимая экономика | Нет click/booking в продукте | Кабинет TP + sub-marker до масштаба креаторов |
| Scope creep | Искушение копировать Hopper/Kiwi/полный поиск | Non-goals §5 + критерии §12 |
| Юр/выплаты | Стратегия компании в roadmap пустая | Закрыть до первых серьёзных CPA-выплат |
| Неверный сегмент | Vision TODO по аудитории открыт | 100 users = интервью, не vanity invites |

## 12. Критерии принятия решений при разработке

Перед любой задачей ≥1 дня ответить «да» на фильтры. Если нет — не берём или явно меняем стратегию в этом файле + [DECISIONS](DECISIONS.md).

### Фильтр A — соответствие USP

Усиливает ли изменение: (1) контракт порога, (2) тишину до события, (3) путь алерт → билеты в Telegram?

### Фильтр B — метрика

Как это сдвинет **Alerted Watchers (30d)** или качество алертов / alert→click? Если ответ «никак, но красиво» — отказ.

### Фильтр C — обязательность vs non-goal

Есть ли в §4 / запрете §5? Non-goal не «попробуем на выходных».

### Фильтр D — честность

Не заставляет ли UI обещать то, чего API не даёт (pax, RT, demo как рынок)?

### Фильтр E — стоимость фокуса

Что *не* сделаем из P0 roadmap, если возьмём это? Если жертвуем стабильностью/антиспамом ради фичи роста — отказ.

### Фильтр F — обратимость

Легко ли откатить? High-irreversible (оплата, юрлицо, смена партнёра) — только с явным решением в DECISIONS.

### Краткая матрица «брать / не брать»

| Сигнал | Решение |
|--------|---------|
| Чинит алерт/uptime/антиспам | Брать |
| Даёт атрибуцию канала или шаринг | Брать после стабильности |
| Копирует фичу гиганта «чтобы было» | Не брать |
| Требует стать OTA/fintech | Не брать |
| Улучшает поиск шире Aviasales | Не наш слой |
| Платежи/лимиты без данных 1k | Отложить |
